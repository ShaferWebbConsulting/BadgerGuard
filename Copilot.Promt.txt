Build a prototype called "Trusted Fusion Gateway" — a secure, zero-trust multi-source data fusion system.

The system should simulate multiple satellite/sensor data sources, fuse their data into a unified event stream, verify integrity using a distributed validation layer, and run analytics in a sandboxed environment.

## Core Requirements

### 1. Data Sources (Simulation)

* Create two simulated data producers:

  * Source A: tracking/position events
  * Source B: anomaly/sensor events
* Each source should emit JSON events over HTTP or WebSocket
* Include fields like: timestamp, source_id, event_type, payload

### 2. Ingestion API

* Build a backend service (prefer Rust with Axum OR Node.js with Express if simpler)
* Accept incoming events from multiple sources
* Normalize events into a unified schema
* Assign unique event IDs and timestamps

### 3. Fusion Service

* Combine related events from different sources into a single "fused event"
* Use simple logic (e.g., same object_id within time window)
* Output a structured fused event:

  * event_id
  * sources[]
  * event_type
  * confidence_score
  * timestamp
  * payload_hash

### 4. Integrity / Validation Layer

* Implement a simplified distributed validation system inspired by asynchronous consensus
* Simulate multiple validator nodes (can run as threads/services)
* Each node:

  * hashes events
  * validates integrity
  * votes/approves events
* Mark events as:

  * "pending"
  * "verified"
  * "rejected"
* Include a basic cryptographic integrity check (hash-based is fine; structure should allow future RSA accumulator integration)

### 5. Sandbox Analytics Module

* Create a containerized analytics service (Docker)
* Accept only VERIFIED events
* Perform simple analysis:

  * anomaly scoring OR classification
* Treat it as an untrusted plugin:

  * isolate execution
  * log all inputs/outputs

### 6. Dashboard (Frontend)

* Build a simple web UI (React or minimal frontend)
* Display:

  * incoming raw events
  * fused events
  * validation status (pending/verified/rejected)
  * analytics output
  * audit logs
* UI can be simple but must clearly show data flow

### 7. Audit & Logging

* Log all stages:

  * ingestion
  * fusion
  * validation
  * analytics
* Include timestamps and event IDs
* Make logs visible in UI or via API

## Architecture Requirements

* Modular structure:
  /services
  /ingestion
  /fusion
  /validation
  /analytics
  /frontend
  /shared (schemas, types)
* Use Docker Compose to run services locally
* Include README explaining how to run the system

## Nice-to-Have (if possible)

* Simulate a malicious or corrupted event and show rejection
* Add basic retry or fault tolerance logic
* Include simple metrics (latency or throughput)

## Goal

The goal is NOT a production system, but a working MVP that demonstrates:

* multi-source data fusion
* zero-trust validation before analytics
* distributed verification concept
* sandboxed analytics execution
* clear visualization of the pipeline

Keep implementation simple but structured for future extension.
